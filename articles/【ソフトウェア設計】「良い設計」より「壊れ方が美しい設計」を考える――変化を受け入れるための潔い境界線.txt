TITLE: 【ソフトウェア設計】「良い設計」より「壊れ方が美しい設計」を考える――変化を受け入れるための潔い境界線

CONTENT:
## 「完璧な設計」という幻想から、一歩引いてみる

ソフトウェア開発に携わっていると、「良い設計」という言葉にどこかプレッシャーを感じることはありませんか。
「変更に強く、拡張性が高く、誰が見ても理解しやすい――」。そんな理想を追い求め、SOLID原則などの設計指針を完璧に守ろうと格闘する日々は、時に私たちを疲れさせてしまいます。

もちろん、原則を知ることは大切です。しかし、どれほど注意深く設計しても、数年後の未来に現れる「想定外の変更」をすべて予測し、完璧に防ぐことは不可能です。

そこで今回は、少し視点を変えてみませんか。
目指すのは、どんな変更にも耐えうる「壊れない設計」ではなく、**「もし壊れるとしても、その壊れ方が美しい設計」**です。

これは決して「適当に作ればいい」という意味ではありません。むしろ、将来の変更に対して「どこまでを自分たちの責任とし、どこからを潔く諦めるか」という、非常に誠実な境界線の引き方の話です。

## 「何でも知っている」クラスが、変化の瞬間に牙を向く

なぜ「壊れ方」を考える必要があるのでしょうか。その理由は、無理に完璧を目指して作った「高機能すぎる構造」ほど、想定外の変更が来たときに無残に崩れ去るからです。

例えば、注文処理を行うシンプルなクラスを想像してみましょう。

```csharp
// 注文処理を行うクラス。一見、普通に見えますが……
public class OrderProcessor
{
    public void Process(Order order)
    {
        // 1. 在庫のチェック（在庫管理の知識）
        if (order.Items.Any(item => item.Stock < 0)) { /* エラー処理 */ }

        // 2. データベースへの保存（永続化の知識）
        Database.Save(order);

        // 3. 完了通知の送信（外部通信の知識）
        EmailService.Send("注文完了", order.CustomerEmail);
    }
}
```

このコードの問題は、`OrderProcessor`が「世界のすべて」を知りすぎていることです。
もし、「通知はメールではなくLINEにしたい」というマーケティング部門の要望や、「保存先をクラウドストレージに変えたい」というインフラチームの都合が重なったらどうなるでしょうか。

* **変更の理由が多すぎる**：誰かが要望を出すたびに、このクラスを修正しなければなりません。
* **壊れ方が醜い**：メール送信を直している最中に、うっかり在庫チェックの変数を触ってしまい、全く関係ない「在庫が減らない」というバグを生むリスクがあります。

これが「醜い壊れ方」です。一つの変更が、関係のない場所にまで飛び火し、システム全体を「触るのが怖い」状態にしてしまいます。

## 潔く「責任」を分かち、壊れる範囲を限定する

「壊れ方が美しい」とは、**「ある場所を直しても、その影響がそこだけで止まる」**状態を指します。
これを実現するのが、SOLID原則の第一歩である「単一責任原則（SRP）」です。

先ほどのコードを、あえて「バラバラ」にしてみましょう。

```csharp
// 1. 在庫をチェックする人（アクター：物流部門）
public class StockChecker { /* ... */ }

// 2. データを保存する人（アクター：IT運用部門）
public class OrderRepository { /* ... */ }

// 3. 通知を送る人（アクター：顧客対応部門）
public class NotificationService { /* ... */ }

// 4. それらを「つなげるだけ」の人
public class OrderApplicationService
{
    public void Execute(Order order)
    {
        _stockChecker.Check(order);
        _repository.Save(order);
        _notifier.Notify(order);
    }
}
```

構造は少し増えましたが、得られる安心感は別物です。
何が変わったのでしょうか。

* **影響の局所化**：通知方法を変えたければ、`NotificationService`だけを修正すればいい。他のクラスは、その変更を知る必要すらありません。
* **壊れ方の透明性**：もし通知機能が壊れても、在庫チェックが止まることは物理的にあり得ません。

「ここが壊れても、あちらは大丈夫」。そう言える境界線を引くことこそが、設計における「誠実さ」だと私は考えています。

## 低レイヤーの視点から：C言語が教えてくれる「物理的な壁」

この「境界線を引く」という感覚は、実はC言語のような制約の多い言語で学ぶと、より解像度が高まります。

C言語には、モダンな言語にあるような便利な「隠蔽」の機能がデフォルトではありません。放っておけば、どこからでも変数を書き換えられる「共有の広場」のようなコードになってしまいます。
だからこそ、熟練の設計者は `static` キーワードを使って、外部からのアクセスを物理的に遮断します。

「ここから先は勝手に入らせない」という物理的な壁を作ることで、不必要な依存関係を根絶するのです。
高級言語を使っているときも、頭の中に「このクラスの周りには物理的な壁があるか？」と思い浮かべてみる。その想像力が、美しい壊れ方を支える土台になります。

## 設計とは「未来の自分への、ささやかな誠実さ」

「良い設計」を目指そうとすると、つい「何が起きても大丈夫な最強の構造」を作りたくなります。しかし、現実のビジネスは、私たちの想像を超えた方向に進化していきます。

だからこそ、私たちは「予測」することに全力を出すのを少しやめて、「分離」することに意識を向けてみませんか。

「この機能とこの機能は、きっと別の誰かが別の理由で変えたくなるはずだ」

そう感じた場所に、そっと一本の線を引く。
その一本の線が、数年後、大きな変更の波が来たときに「ここだけ直せば大丈夫ですよ」と未来の自分を助けてくれるはずです。

完璧を目指すのではなく、潔く、美しく壊れる準備を整える。
そんな謙虚な設計が、結果として最も長く愛されるソフトウェアを作るのかもしれません。

この考え方が、あなたのプロジェクトの新しい視点になれば幸いです。
