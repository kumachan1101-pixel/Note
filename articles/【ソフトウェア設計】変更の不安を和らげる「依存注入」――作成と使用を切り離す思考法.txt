TITLE:【ソフトウェア設計】変更の不安を和らげる「依存注入」――作成と使用を切り離す思考法

CONTENT:
## 「変わるかもしれない」という不安とどう向き合うか

ソフトウェア開発において、最も確実なことは「いつか変更がやってくる」ということかもしれません。
データベースの種類が変わる、ログの出力先が変わる、外部APIが別のサービスに置き換わる。そうした変化の足音が聞こえるたびに、既存のコードを壊してしまうのではないかという不安を感じた経験は、多くの開発者にあるのではないでしょうか。

この「変更への不安」を和らげるための一つのアプローチとして、「依存注入（Dependency Injection, DI）」という考え方があります。
用語だけを聞くと少し難しく響くかもしれませんが、その本質は「オブジェクトが使う道具（依存）を、自分で調達するのではなく、外から渡してもらう」という非常にシンプルな構造です。

今回は、この依存注入がなぜ生まれたのか、そして私たちのコードにどのような変化をもたらすのかを、「依存の作成」と「依存の使用」という視点からひも解いてみたいと思います。

## 道具を自分で作ってしまうことの不便さ

まず、あるクラスが別のクラスの機能を使うときのことを考えてみます。
例えば、ユーザーの情報を登録する処理を書く場合、データベースに保存するための機能が必要になります。

直感的にコードを書くと、次のような形になることがよくあります。

```csharp
public class UserService
{
    private SqlUserRepository _repository;

    public UserService()
    {
        // クラスの中で直接、具体的な道具（SQL用リポジトリ）を作ってしまう
        _repository = new SqlUserRepository();
    }

    public void RegisterUser(string name)
    {
        _repository.Save(name);
    }
}
```

このコードは素直で読みやすい反面、いくつかの不便さを抱え込むことになります。

* **テストがしづらい**：`UserService`のテストをする際、常に本物のSQLデータベースに接続しようとしてしまいます。
* **変更のたびにコードを触る必要がある**：もし将来、「データをメモリに一時保存する仕組みに変えたい」となった場合、`UserService`の中の `new SqlUserRepository()` という部分を直接書き換えなければなりません。

こうした問題の根本は、`UserService`が「具体的なデータベースの実装」を深く知りすぎてしまっていることにあります。

## 「使い方」だけを知っていれば良い構造に変える

この状況を改善するための考え方が、依存注入と「抽象（インターフェース）への依存」です。
「どんな種類のデータベースを使うか」という具体的な実装ではなく、「データを保存できる何か」という抽象的なルールにだけ関心を持たせるようにコードを変えてみます。

```csharp
// 「名前を保存できる」という抽象（インターフェース）
public interface IUserRepository
{
    void Save(string name);
}

public class UserService
{
    private readonly IUserRepository _repository;

    // 具体的な道具は、外部（コンストラクタ）から渡してもらう
    public UserService(IUserRepository repository)
    {
        _repository = repository;
    }

    public void RegisterUser(string name)
    {
        _repository.Save(name); // 具体的にどこに保存されるかは気にしない
    }
}
```

このように形を変えると、`UserService`は、渡されたものがSQL用なのか、ファイル保存用なのか、あるいはテスト用のダミーなのかを知る必要がなくなります。
ただ「渡された道具の `Save` メソッドを呼ぶ」という自分の責務に集中できるようになります。

* **実装の変化に気づかない**：外部から渡されるクラスが `SqlUserRepository` から `MemoryUserRepository` に変わっても、`UserService` のコードは1行も修正する必要がありません。
* **機能の差し替えが容易**：変わりやすい機能（DB、ログ出力など）をインターフェース越しに扱うことで、システム全体が柔軟になります。

## 依存の「作成者」と「保持期間」という2つの視点

ここで少し視点を変えて、コードの中にある「依存関係」を整理してみたいと思います。
依存関係は、「誰がそのオブジェクトを作ったか」と「どのくらいの期間保持するか」という2つの軸で、以下の4つのパターンに分類できると考えられます。

* **パターン1：自身が作成 × 長期間保持**
    クラスの中で `new` を使い直接作成し、メンバー変数として持ち続ける形です。先ほどの「不便だった最初の例」がこれに当たり、特定の機能との強い結びつきを生みやすくなります。
* **パターン2：自身が作成 × 短期間保持**
    メソッドの中で `new` して、その処理が終わったら使い捨てる形です。
* **パターン3：他人が注入 × 長期間保持**
    コンストラクタなどを通じて外部から受け取り、メンバー変数に保持する形です。改善後の「依存注入」の例がこれに該当します。
* **パターン4：他人が注入 × 短期間保持**
    メソッドの引数として受け取り、その場限りで使用する形です。

では、この「他人が注入」するパターンにおいて、「いつ、誰がその依存（道具）を作るのか？」という疑問が湧くかもしれません。
使う側（UserService）が作らないのだとすれば、誰かが代わりに作って渡してあげる必要があります。

これを担当するのが、「ファクトリークラス」やアプリケーションの根元にある設定部分（DIコンテナなど）です。

```csharp
// 依存の作成と組み立てだけを担当する場所
public class UserServiceFactory
{
    public static UserService Create()
    {
        // ここで具体的な実装を決定し、注入する
        IUserRepository repository = new SqlUserRepository();  
        return new UserService(repository);
    }
}
```

このように、「実際に処理を実行する人」と「どの部品を使うかを選んで組み立てる人」を明確に分けることで、コードの居場所がすっきりと整理されていきます。

## システムを「つなぎ変え可能」なブロックとして捉える

依存注入を活用するということは、単にコンストラクタの引数を増やすということではなく、ソフトウェアを「つなぎ変え可能なブロックの集まり」として設計し直すというアプローチです。

変わりやすい外部システムやインフラへのアクセスを抽象化し、組み立てる責任を外側に追い出すことで、中核となるロジックは外のノイズから守られます。それは結果として、「ここを直したら別の場所が壊れるかもしれない」という開発者の不安を減らすことに繋がります。

もちろん、すべてのクラスをインターフェース越しに設計する必要はありません。変化しにくい安定したロジックであれば、直接依存したほうがシンプルな場合もあるでしょう。

大切なのは、「今書いているコードは、将来どのように変化しそうか？」と想像を巡らせることかもしれません。その際に、依存注入という道具が一つの選択肢として、あなたのプロジェクトを助けるヒントになれば幸いです。
